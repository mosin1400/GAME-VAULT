# P00–P03 implementation progress

Evidence: [machine-readable receipt](evidence/2026-09-15-p00-p01.json).

## Completed source work

- Binary inventory, manifest validation, streaming backup, copied-tree verification and fresh-target restore are implemented. Seven behavioral tests pass, including environment exclusion, >1MB binary preservation, junction rejection, overlap, stale source, tampering and manifest traversal.
- Real external backup and a separate restore preserve 467 files byte-for-byte. Four protected environment paths were excluded before open/hash/copy. Windows backup-parent ACL was restricted successfully. The receipt is NOT a complete credential recovery set.
- Static publication now uses an explicit frontend catalog and a temporary versioned-game web-asset policy, rather than arbitrary workspace-root fallback. Protected paths and private server/account/configuration files are rejected before filesystem access; unknown paths return 404. Physical links/hardlinks fail closed, validated handles preserve exact bytes, errors do not return host paths. HEAD/405 and nosniff are covered.
- Deleted-editor references were removed from existing tests. Only the retired editor-chat-only test was deleted; actual Theia coverage was preserved. System tools now test a disposable binary fixture. Unversioned imports remain pending classification rather than receiving fabricated metadata.
- `npm.cmd test` passes: 45 surviving root contracts, 11 behavioral tests and 10 typed API tests. HTTP smoke with the actual source tree on an isolated loopback handler confirms dashboard/Theia entry/shared assets/two playable HTML paths 200 and private/missing paths 404. This does not test actual IDE launch or native PTY.
- The active 8080 service now runs the hardened source, with a verified graceful lifecycle. The fresh full run also proves the API entrypoint, authorization policy and actor-bound transaction helper without touching environment files.
- `apps/api` is a separate strict TypeScript/Fastify boundary. Its `buildApp` factory receives configuration/dependency readiness explicitly, has no environment-file access, exposes `/health/live` and `/health/ready`, emits request IDs, and returns stable redacted error shapes. It is intentionally not yet a replacement router for legacy domains.
- The P03 authorization model is implemented as a typed, tested policy boundary and additive PostgreSQL migrations. It establishes immutable UUID IDs/storage keys, owner/member roles, RLS/FORCE RLS, version revision fields and append-only audit/operation rows. Every database transaction validates an actor UUID and sets the actor locally before domain work, then commits or rolls back and releases its connection. PostgreSQL itself is not provisioned in this workspace, so migration/RLS acceptance remains pending rather than claimed.
- P04 now has an additive identity-security migration and framework-independent policy modules. Password verifiers, session/CSRF hashes and email/OIDC secrets are independent rows rather than columns on `users`; password input is never normalized; sessions have 24-hour idle and 30-day absolute lifetimes and are invalid after revocation, auth-epoch change, expiry or account suspension; post-login redirects accept only validated local paths, rejecting origin escapes and double-encoding. It is not yet an enabled registration/login route, because no disposable PostgreSQL or mail sink is available for its end-to-end acceptance.
- P05 has begun with a binary-safe source-manifest boundary, verified local staging/commit adapter and explicit operation-journal state machine. Manifests preserve raw-byte SHA-256/length data for Unicode paths and reject directory links/special files instead of traversing them. A changed source or tampered staging tree cannot be promoted; failed staging cleans only its operation-owned temporary tree, while suspicious staged bytes remain for reconciliation. The local journal proves idempotent retry and only permits `pending → running → bytes_ready → succeeded` (or an explicit failure/cancel) transitions. This is not yet the required durable PostgreSQL journal, reconciler or database publish pointer.

## Gates still open

- Writer ownership/freeze was not established; unrelated listeners were not stopped. Hash agreement is not a transactional maintenance epoch. No product-data migration or live-data restore was performed.
- Root and Theia dependencies were clean-installed from preserved lockfiles (1,156 Theia packages). Theia browser build completed with zero errors. Node build is blocked at `@vscode/windows-ca-certs`: its `crypt32.node` addon needs a supported Visual Studio C++ workload for Node 24, which is absent. This is a real environment gate, not a test change; `runtimeVerified:false` is intentional. The generated frontend also reflects a broader historical Theia set than the current manifest and needs reconciliation before production rebuild.
- The verified IPv6 8080 `node server.js` process was replaced with the hardened source. Live status-only smoke checks confirm active public pages/playable game return 200 and `/server.js`, backend auth source, vault users, removed editor and missing paths return 404. The application performs its own normal startup configuration loading to preserve AI behavior; this task never opened, copied, printed or logged `.env` content. The service now has an idempotent graceful shutdown lifecycle for its HTTP server and any managed Theia child.
- Theia host shell/terminal isolation, durable identity/ACL, snapshot recovery, transactional community, React/SSE and production deployment remain separate planned packages. P01 static checks are not proof of workspace isolation or user-content-origin security.
- A live PostgreSQL deployment, real mail delivery/Argon2 adapter and isolated per-user Theia workers are not safe “cleanup” changes to fold into a deadline patch. They remain P04/P09 activation gates.
